## Architecture changes

The stateful implementation now lives under `internal/engine`. Stable leaf logic remains split into `internal/core`, `internal/escscan`, `internal/inputparser`, and `internal/textutil`. Public packages remain domain-oriented (`widgets`, `layout`, `text`, `render`, `input`, `interaction`, `selection`, `terminal`, `scheduler`).

The root compatibility API is generated by `internal/cmd/genapi`:

```bash
go generate ./...
```

## Bugs found in this round

Two correctness bugs were found by hardening rather than parity fixtures:

1. `FocusManager.Disable()` blocked direct `Focus()` but `FocusNext()`/`FocusPrevious()` could still return a node as though focus had changed. Traversal/autofocus now fail closed while disabled.
2. `scheduler.Clock.Every` had a real data race because timer ticks could overlap callback execution and concurrently access the interval accumulator. Shared-clock ticks are now non-reentrant: the next timer is armed only after the callback batch completes. The regression passes under the race detector.

## 10,000-row ScrollBox stress

An early Round-5 stress run exposed the dominant production issue: scrolling a materialized 10,000-row tree recomputed/traversed too much static state. An observed 100-frame loop took about 12.2 seconds before the first optimization pass.

The final design adds:

- separate layout-dirty and paint/scroll-dirty invalidation;
- cached geometry reuse for scroll-only frames;
- layout-certified linear-Y children and binary-search visible-range painting;
- root-local layout indexes for scroll/button controls instead of repeated 10k-node discovery walks;
- dirty-subtree clearing that stops at already-clean branches;
- reusable renderer scratch framebuffer for fullscreen hardware-scroll simulation.

Final benchmark on the validation host (AMD EPYC 9V74, Go 1.23.2, `GOMAXPROCS=2`):

```text
BenchmarkRendererStableSnapshot       ~543,173 ns/op   ~547,626 B/op   188 allocs/op
BenchmarkRendererBorrowed             ~307,530 ns/op    ~21,907 B/op   175 allocs/op
BenchmarkScroll10KWarm                ~114,183 ns/op     ~6,729 B/op    98 allocs/op
BenchmarkLargeHistoryFirstFrame10K    ~130,167,391 ns/op ~65.6 MB/op  ~1.28M allocs/op
```

The first 10k frame intentionally includes construction/measurement of 10,000 concrete nodes and remains O(n). Warm scroll no longer scales its administrative work with all 10,000 rows.

## Profiling

Before layout indexes, `Node.Walk` and scroll/button rediscovery dominated the warm-scroll CPU profile. In the final profile those full-tree administrative scans disappeared from the top entries; visible framebuffer work (`ScreenDamage`, `DiffScreens`, cell/style comparisons) became the dominant engine cost.

The reusable hardware-scroll scratch screen removed the per-frame full-screen simulation clone. Warm 10k scroll fell from roughly 211 KB/frame at an intermediate Round-5 checkpoint to about 6.7 KB/frame in the final benchmark.

## Retention and long-running behavior

Regression tests now verify that:

- 250 scroll updates on a 10k-row tree reuse layout geometry;
- 2,000 text mutations retain only the current per-node bounded cache entries;
- replacing scroll roots 1,000 times does not accumulate detached scroll-node state in the renderer;
- terminal writes remain serialized;
- scheduler ticks do not overlap slow subscribers.
